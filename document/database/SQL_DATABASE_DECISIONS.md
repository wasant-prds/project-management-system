# SQL database decisions — Issue #31

Updated 2026-10-04 to follow the current project queries and naming review.
The SQL snapshot is a draft empty target. Active runtime remains `prisma/schema.prisma` with CUIDs and guarded `prisma db push`.

## Current implementation

1. Keep the 11 business tables used directly or through Project DELETE relation counts. Exclude unused `Comment`, `Notification` and the future `legacy_id_mapping` table. Keep `schema_migrations` because the current SQL runner reads and writes it. Retaining a deletion-guard relation does not mean it has a CRUD feature.
2. Use plural snake_case table names and snake_case columns, enum types, indexes and constraints. Use `work_logs` for TimeEntry, `password_hash` for stored credential hashes, `functional_role` for a work item function, `type_labels` for WorkItem types, and `work_date` for the work log calendar date. All table and column descriptions are PostgreSQL `COMMENT ON` metadata. See the complete field mapping and source evidence in [schema dictionary](SQL_SCHEMA_DICTIONARY.md).
3. User-approved identifier contract: every table also has immutable random UUIDv4 public_id (NOT NULL, UNIQUE, database default gen_random_uuid). API/frontend references use public UUIDs; decimal numeric IDs are internal tooling only. All mutable-table timestamp triggers reject public_id changes even with timestamp-preservation enabled; immutable activity/migration rows already reject all updates. See [public identifier contract](PUBLIC_IDENTIFIERS.md). Every primary key is `BIGINT GENERATED BY DEFAULT AS IDENTITY (START WITH 1 INCREMENT BY 1 NO CYCLE)`. Each table owns its sequence. Gaps from rollbacks/deletes/conflicts are allowed; never renumber rows or use `MAX(id)+1` for ordinary inserts. `pms_align_identity(regclass)` aligns a sequence after explicit-ID imports, including empty tables.
4. Local relation keys are BIGINT. `ExternalWorkItemReference.projectId` is a local PMS project ID according to `lib/gitlab-issue-import.ts`, so its target `project_id` is BIGINT with a project FK. External GitLab project/issue/IID values and the polymorphic `activity_logs.entity_id` stay TEXT. Old CUID project references require ID translation before numeric import.
5. Keep legacy nullability, default values, decimal precision and enum literals. `in-progress`, `sa-testing`, `pm-testing` and `special-dark` are unchanged. Project budget/spending and work log hours use DECIMAL(65,30). Renaming fields does not redefine their data units or backfill their values.
6. Mutable business tables have `created_at` and `updated_at` TIMESTAMP(3) WITHOUT TIME ZONE. Activity history has only `created_at` and rejects UPDATE/DELETE. Its user/project FKs restrict DELETE and UPDATE so cascade changes cannot rewrite history. Migration history uses `applied_at` and rejects UPDATE/DELETE.
7. `pms_bangkok_now()` and `pms_bangkok_today()` explicitly use Asia/Bangkok independent of session TimeZone. Ordinary INSERTs stamp local timestamps. UPDATE preserves created_at and advances updated_at only on business changes. Controlled imports can preserve timestamps with `set_config('pms.preserve_source_timestamps','on',true)` in the same transaction. Remote source timestamps are separate from local history.
8. Migration 0001 references the single `database/schema.sql` file. The manifest SHA-256 hashes its exact bytes and is refreshed for this draft revision. The runner owns the transaction, advisory lock, 5-second lock timeout and 120-second statement timeout. Changed applied checksums are rejected; this edited baseline is not an upgrade script for an already bootstrapped target.
9. `empty-bootstrap` requires an empty public schema. `upgrade` requires recognized `schema_migrations` history. Targets without that history but with existing public tables are rejected. The active application database and known APP_ENV container names are rejected. URL passwords are passed through PGPASSWORD rather than argv.
10. Catalog fingerprints include table/column comments, so documentation drift is detectable as well as DDL drift.
11. External integration naming is provider-neutral by user request: `external_project_mappings` and `external_work_item_references` use `provider`, `instance_url`, `external_project_id`, with references adding `external_issue_id` and `external_issue_number`. Mapping source uniqueness includes provider/instance/project; reference uniqueness also includes the stable issue ID. Defaults remain gitlab, both provider namespaces can coexist, and one reference per local work item is retained. Unmapping never deletes imported work items/references. Mapping provider plus 12 public_id columns bring the snapshot to 12 tables/145 columns; every column remains documented.

## Remaining rollout work

- The active Prisma schema still contains 13 CUID business models. Future SQL runtime cutover must map every renamed model, field and enum and expose public UUIDs through explicit DTOs. No current API has switched to the public UUID contract; internal bigint never becomes a client-visible ID.
- GitHub synchronization is not implemented by this naming change. At #33 cutover, add provider to the Prisma mapping model, update compound identities and explicitly scope GitLab mapping/reference reads and mutations to provider=gitlab. The generic table name alone does not isolate GitLab consumers from future GitHub records.
- Any source-to-numeric data migration must implement and verify its required ID provenance storage when that migration exists. `scripts/sql-legacy-id.mjs` currently only validates and sorts in-memory mapping records; its helper tests do not justify creating an unused persistence table now.
- Public UUID/internal numeric separation is approved by the user. Activity history immutability remains a draft foundation choice; production cutover is separate.
- The timestamp-preservation setting is not restricted by database role and is not a security boundary.
- No new CHECK constraints for positive hours, progress 0–100 or timestamp order are introduced before reviewing existing data. Work log linkage remains nullable in storage while the current API requires a work item.
- User joined_at and milestone due_date retain timestamp types. Converting legacy timestamps to DATE, fixing anomalies and customer assignment remain data migration decisions.
- No automatic downgrade is provided. Existing targets using the prior baseline cannot consume this edit through upgrade; a reviewed migration or a new isolated empty fixture is required.
