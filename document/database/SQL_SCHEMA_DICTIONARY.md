# SQL schema dictionary — Issue #31

Updated 2026-10-04 after comparing the snapshot with the current application source.
The source of truth for DDL is `database/schema.sql`. Issue #33 maps `prisma/schema.prisma` onto that snapshot. A database that still stores CUID primary keys is not a compatible target, and this repository change does not cut one over.

## Naming and scope

Tables use plural `snake_case`; columns, indexes, constraints, triggers and enum types use `snake_case`.
Every table and column has a database-visible PostgreSQL `COMMENT ON` statement in the snapshot.
There are 11 business tables referenced by current application queries, plus `schema_migrations` required by the SQL runner.

`Comment` and `Notification` occur in the legacy Prisma/seed model but have no current application queries, so they are excluded from this target.
`legacy_id_mapping` is future migration infrastructure with no current database reader or writer and is also excluded.
`project_members`, `project_documents`, `project_milestones` and `activity_logs` are retained because the current Project DELETE route counts them before allowing deletion. This does not imply that these features have active CRUD endpoints.

## Internal and public identifiers

Every table, including schema_migrations, has two identifiers: numeric identity id for PK/FKs and immutable public_id UUID NOT NULL UNIQUE, generated by pg_catalog.gen_random_uuid(). Public API/UI/URLs and DTO id/related *Id fields use the related row's canonical UUIDv4; storage relations use only BIGINT. `publicId` maps to `public_id`. The schema enforces generation, uniqueness, nullability and immutability. Issue #33 application code validates canonical UUIDv4 and returns explicit DTOs. See [public identifier contract](PUBLIC_IDENTIFIERS.md).

## External provider contract

The mapping table is `external_project_mappings`, shared by providers such as `gitlab` and `github`. Both mappings and external issue references use `provider`, `instance_url` and `external_project_id` to identify their source. An external project can be a provider project or repository; it is separate from the local PMS `project_id`.

Mapping uniqueness is `(provider, instance_url, external_project_id)`. Issue reference uniqueness is `(provider, instance_url, external_project_id, external_issue_id)`. Equal source IDs can coexist across providers or instances. `external_issue_number` is the project/repository-scoped issue number, such as the current GitLab IID; it does not replace the stable `external_issue_id`. Deleting a mapping retains imported work items and references. One external reference per local work item remains the current contract.

`provider` defaults to `gitlab` for the existing importer and is stored as TEXT rather than a provider-specific enum. There are no separate GitHub tables. GitHub sync is not implemented. Issue #33 stores `provider` on both mapping models and filters GitLab reads, mutations and sync with `provider = 'gitlab'`.

## Data rules

Local timestamps are `TIMESTAMP(3) WITHOUT TIME ZONE` using Bangkok wall-clock time. Calendar dates remain `DATE` and financial amounts/hour durations retain `DECIMAL(65,30)`.
Mutable business tables have `created_at` and `updated_at`; activity logs have only `created_at` and reject updates/deletes. Migration history uses `applied_at` and is immutable.
Ordinary writes use timestamp triggers; controlled imports can preserve source timestamps using `pms.preserve_source_timestamps`. That setting is not a permission boundary.
`work_logs.project_id` and `work_item_id` retain legacy nullability in storage; current create requests require a work item and derive its project. The API checks positive hours. Project progress is derived from work item states by the API; `progress_percent` retains the legacy stored value.

- `project_members.project_id` → `projects.id`; DELETE RESTRICT, UPDATE CASCADE.
- `project_members.user_id` → `users.id`; DELETE CASCADE, UPDATE CASCADE.
