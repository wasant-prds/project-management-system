# SQL runtime, public UUIDs, existing-data conversion and recovery — Issue #33

ตรวจ implementation ล่าสุด: 2026-10-06. วันและ timestamp ของระบบใช้ `Asia/Bangkok`; timestamp ที่บันทึกเป็น Bangkok local wall-clock และไม่แปลงเป็น UTC.

## ขอบเขตและสถานะ

Issue #33 เชื่อม Prisma/API/startup เข้ากับ [SQL schema และ migration ของ Issue #31](./issue-31-sql-schema.md) และ [SQL master seeds ของ Issue #32](./issue-32-sql-master-seeds.md). หน้านี้อธิบาย runtime, identity boundary และเครื่องมือแปลงข้อมูลที่ตรวจได้จาก source ปัจจุบัน.

ยังไม่มีการ migrate, seed, reset, deploy หรือ cutover ฐานข้อมูลที่ใช้งานอยู่. อย่าชี้ build นี้ไปยังฐานข้อมูล legacy ที่ยังใช้ CUID เป็น primary key. Live cutover ต้องมี baseline ใหม่ที่ verified, run record ที่ผูก target และ explicit authorization แยกต่างหาก.

## Identity ในฐานข้อมูลและ API

ตารางธุรกิจปัจจุบันมี `id BIGINT GENERATED BY DEFAULT AS IDENTITY` สำหรับ PK/FK ภายใน และ `public_id UUID NOT NULL DEFAULT gen_random_uuid()` สำหรับอ้างอิงจาก client. `public_id` ต้องเป็น UUIDv4 และ immutable. SQL join/FK ใช้ numeric `id`; DTO, URL, UI, import/export ที่ส่งออก และ API relation fields ใช้ public UUIDv4. ดู [Public identifier API contract](../api/record-identifiers.md).

ตารางธุรกิจคือ `users`, `companies`, `projects`, `project_members`, `work_items`, `external_project_mappings`, `external_work_item_references`, `project_milestones`, `project_documents`, `work_logs` และ `activity_logs`; `schema_migrations` เก็บสถานะ migration. ความสัมพันธ์ตัวอย่างคือ `projects.company_id → companies.id`, `work_items.project_id → projects.id` และ `work_logs.work_item_id → work_items.id`.

DTO สร้างจาก explicit serializers โดย `id` มาจาก ORM `publicId`; nested `companyId`, `projectId`, `workItemId` และ `assignee.id` ก็อ้าง public UUID ของ record ที่สัมพันธ์. Numeric internal IDs/BigInt ไม่ถูกส่งเป็น JSON. Cursor pagination เข้ารหัสและผูกกับ owner/filters; cursor base64 JSON รุ่นเก่าใช้ไม่ได้.

`OWNER_USER_ID` ใช้ public UUID หรือ legacy source ID ที่ resolve ผ่าน live mapping; numeric ID ถูกปฏิเสธ. ถ้าไม่กำหนดค่า ระบบยอมใช้ owner เฉพาะเมื่อพบ User เพียงหนึ่งรายการ. `Developer`, `infra`, `SA` เป็น WorkItem functional roles ไม่ใช่ permissions. ทุก business API ยังต้องผ่าน owner access gate และ object scope; ดู [Owner access](../operations/owner-access.md).

## Startup และ SQL runtime

Compose `migrations` service รอ PostgreSQL healthy. `scripts/docker-entrypoint-migrate.sh` ตั้ง Bangkok timezone, สร้าง encoded `DATABASE_URL` จาก `POSTGRES_*`, ตั้ง `PMS_SQL_RUNTIME_APPLY=1`, ตรวจ schema rollout approval, generate Prisma Client แล้วเรียก `node scripts/sql-runtime.mjs apply`. `psqlTarget()` ตัด Prisma-only `schema`, `connection_limit`, `pool_timeout`, `pgbouncer`; เก็บ libpq options และส่ง password ผ่าน `PGPASSWORD` แทน argv ของ `psql`.

`PMS_SQL_RUNTIME_APPLY` ต้องเป็น `1`. Runtime ปฏิเสธ `reset`, `force-seed`, `force`, `accept-data-loss` และ data-loss flags. State handling:

| Database state | Runtime behavior |
| --- | --- |
| ไม่มี migration history และไม่มี public table | bootstrap ด้วย baseline ที่โหลดและตรวจ checksum แล้ว |
| ไม่มี migration history แต่มี table/data | หยุดก่อนเขียน: populated database ไม่มี SQL history ที่อนุมัติ |
| มี migration history | ตรวจ migration version/checksum และ apply เฉพาะ migration ที่ยัง pending ผ่าน SQL runner |

Migration ใช้ transaction/advisory lock และ `Asia/Bangkok`; target ที่ตรงกับ active `DATABASE_URL` หรือชื่อ application container ถูกปฏิเสธ. Startup shell retry เฉพาะ connection errors ชั่วคราวตาม `MIGRATION_MAX_ATTEMPTS` (default `3`) ด้วย backoff; checksum, invalid target และ contract errors ไม่ถูก retry.

## Schema rollout gate

เปิด schema sync ด้วย `DB_SCHEMA_SYNC_APPROVED=true` เท่านั้น. `APP_ENV` ต้องเป็น `local`, `dev`, `uat` หรือ `prod` และเป็น environment ที่อนุมัติ. Gate คำนวณ fingerprint จาก `prisma/schema.prisma`, SQL contract และ `DATABASE_URL` แล้วผ่านเมื่อคำนวณได้. ค่าเหล่านี้ไม่ถูกอ่านจาก `.env`.

| ค่าที่คำนวณ | ความหมาย |
| --- | --- |
| target | fingerprint ของ protocol/host/port/database/user/`APP_ENV`; ไม่รวม password |
| schema | SHA-256 ของ `prisma/schema.prisma` |
| SQL checksum | checksum ของ SQL baseline |
| revision | revision ใน migration contract |
| migrations | ordered version/script/checksum ของ migration ทั้งชุด |
| release | fingerprint รวม revision, SQL checksum, Prisma schema hash, migration list และ target hash |

ฐานข้อมูลว่างที่ไม่มี SQL history bootstrap ได้เมื่อ `DB_SCHEMA_SYNC_APPROVED=true`. ฐานข้อมูลที่มี history และมี migration ค้างจะ apply ได้เมื่อ `BACKUP_DIR` มี receipt ที่ตรวจครบ. ใน container path นี้คือ `/run/pms-rollout-backups`. Receipt ต้องเป็น `.verified.json` ที่ `result` เป็น `isolated-restore-passed`, site ตรง `APP_ENV`, `verifiedAt` ภายใน 24 ชั่วโมง และ SHA-256 ตรงกับ manifest และ bytes ของ archive. ไฟล์บันทึกใช้ `backup-restore` เมื่อ receipt ผ่าน, `empty-database` หลัง bootstrap ฐานว่าง และ `unverified` เมื่อยังไม่ยืนยัน receipt. ถ้าเขียนไฟล์บันทึกไม่ได้ startup ยังทำงานต่อ.

คำสั่ง `node scripts/db-schema-rollout-gate.mjs approve` หรือ `fingerprint` เขียน `database/rollout/schema-approval.json` และพิมพ์ record เดียวกัน. คำสั่งไม่เชื่อมต่อ database และไม่แสดง credentials. ไฟล์นี้ถูก gitignore. `RUN_SEED=true` คนละเรื่องกับ schema approval.

## Seed gate

`RUN_SEED` default คือ `false`; startup ปกติจึงไม่ replay SQL snapshot. เมื่อเป็น `true` seed ทำงานโดยไม่ต้องวาง fingerprint ใน `.env`. `DB_MANAGE_MODE=seed` ยังตรวจ schema approval ก่อน; `reset` และ `force-seed` ถูกปฏิเสธก่อนเขียน.

## Existing-data conversion และ rehearsal

`scripts/sql-live-upgrade.mjs apply` เป็น converter/loader สำหรับ verified archive ไปยัง **replacement target ที่ระบุชัดเจน**; ไม่ใช่ startup migration และไม่มี live cutover command. Source ต้องเป็น PostgreSQL custom `.dump` พร้อม `.dump.json` และ `.dump.verified.json` ที่ site ตรง `APP_ENV`, checksum/bytes ตรงกัน, ผ่าน isolated restore และ verified ภายใน 24 ชั่วโมง. Converter restore source ใน PostgreSQL 16 ephemeral container `--network none`, ปฏิเสธ source table ที่ไม่มี preservation rule และลบ container ชั่วคราวหลังอ่านข้อมูล.

รองรับ schema family legacy และ newer legacy ที่มี Company fields/theme/locale/GitLab mappings. Replacement target ต้องมี schema/migrations ครบตาม revision ที่ตรวจแล้วและ business tables ว่าง. Target ต้องต่างจาก active `DATABASE_URL` และ application container. Converter ไม่ cast CUID เป็นตัวเลข.

ก่อนใช้ converter ต้องผ่าน guards ของ `APP_ENV`, explicit `PMS_LIVE_UPGRADE_APPROVED=true`, source write freeze, final delta reconciliation และ owner mapping review. Target fingerprint และ source archive checksum ถูกคำนวณจาก `--target` กับ archive ที่ตรวจแล้ว โดยไม่รับค่า SHA-256 จาก environment. ก่อนโหลด source ระบบพิมพ์ fingerprint ทั้งสองค่า และไม่พิมพ์ credential. `OWNER_USER_ID` resolve User ด้วย UUID หรือ legacy source mapping; numeric key ไม่รับ. Company assignment ที่ source ไม่มีต้องกำหนดด้วย reviewed policy; ห้ามเดา Company จาก seed snapshot.

ตัวอย่าง policy ใช้เฉพาะ source IDs ที่ผ่านการตรวจ; map Project legacy ID ไปยัง Company legacy ID:

```json
{
  "projectCompanyMap": {
    "<source-project-id>": "<source-company-id>"
  },
  "defaultProjectCompany": "<source-company-id>"
}
```

รูปแบบ CLI ซึ่ง `<...>` เป็น placeholder ไม่ใช่ target พร้อมใช้งาน:

```text
node scripts/sql-live-upgrade.mjs apply --source <verified.dump> --target <replacement-postgresql-url> --mapping <restricted-live-mappings.json> --preserve <restricted-preservation.json> --company-policy <reviewed-company-policy.json>
```

`--source`, `--target` และ `--mapping` จำเป็น. `--preserve` ต้องส่งเมื่อ source มี `Comment`, `Notification` หรือ history tables ที่ไม่มีปลายทาง; ไฟล์ preservation ต้องอยู่นอก repository. Mapping เป็น durable `sourceScope=live` register ที่เก็บ source ID → numeric ID + UUIDv4, เขียนแบบ atomic/restricted และ reuse เมื่อ rerun; ห้ามใช้ seed mapping แทน. ไฟล์ mapping/archive อาจมีข้อมูลอ่อนไหวและต้องเก็บตาม access/retention policy. CLI รับ replacement URL ด้วย `--target`; ถ้า URL มี password ค่าอาจปรากฏใน process argv ของ Node จึงต้องตรวจวิธีส่ง credential และการจำกัด process inspection ก่อน live use.

Load ใช้ transaction เดียว, advisory lock, exclusive lock ตารางธุรกิจ, `lock_timeout=5s`, `statement_timeout=120s`, Bangkok timezone และ `pms.preserve_source_timestamps=on`. ก่อน commit ตรวจ target ว่าง, insert rows, เปรียบเทียบ identity และทุก typed column รวม null/Decimal/date/timestamp/JSON/array, ตรวจ row counts แล้ว align identity sequences. Failure rollback transaction; เก็บ source database ไว้. หลัง commit ตรวจ counts ซ้ำและคืน summary โดยไม่คืนข้อมูล credential.

`exportPostCutoverWrites()` เป็น exported helper สำหรับ export inserted/updated rows และ deleted public IDs หลัง `cutoverAt` Bangkok local timestamp; path output ต้องอยู่นอก repository. ปัจจุบัน CLI รองรับ `apply` เท่านั้น: ไม่มีคำสั่ง standalone สำหรับ export, database restore หรือ cutover. `rollbackPlan()` เป็นแผน decision เท่านั้น. หลังมี writes ใน replacement ต้อง export/reconcile ก่อน restore baseline มิฉะนั้น writes หลัง cutover สูญหาย. การยอมรับ data-loss/RPO และการสลับ application target ต้องผ่าน review/authorization แยก.

## API ที่เกี่ยวข้อง

Issue #33 เปลี่ยน ID contract ของ Route Handlers เดิม ไม่ได้เพิ่ม API route. Path IDs ของ Company, Project, WorkItem, WorkLog และ GitLab mapping รวมทั้ง local relation references ใช้ canonical lowercase UUIDv4; collection filter references ก็ใช้ public UUID. ดู route payload/status/errors ใน [API Handbook](../api/record-identifiers.md) และหน้า endpoint ที่เชื่อมจาก [Handbook index](../README.md). `GET /api/health` เป็น public infrastructure probe; query `schema_migrations` และ session timezone แล้วตอบเพียง status, timestamp, database state และ uptime — ไม่เผย hash/revision.
